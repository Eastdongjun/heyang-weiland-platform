## 1. 架构概览与设计理念

### 1.1 系统定位

合阳洽川湿地智慧管理平台是一套面向湿地生态保护、防火监控、应急指挥的综合管理系统。系统覆盖**视频监控、AI 烟火检测、无人机管理、GIS 地图、IoT 传感器、告警引擎、工单管理**七大业务域，服务两类核心用户角色（指挥中心人员、巡逻人员），支撑**防火闭环、无人机巡逻闭环、环境监测闭环**三大业务闭环。

### 1.2 核心设计原则

| 原则 | 描述 |
|------|------|
| **分层解耦** | 按"感知-传输-数据-服务-应用"五层划分，每层独立演进，职责清晰 |
| **事件驱动** | 核心业务流程以事件/消息驱动，削峰填谷，异步解耦，告警端到端延迟 ≤5s |
| **流式优先** | 视频流、传感器流、告警流均采用流式处理架构，低延迟、高吞吐 |
| **实用高可用** | 单机主从+每日备份，99% 可用性（年均故障 ≤87 小时），满足湿地管理实际需求 |
| **安全纵深** | 传输加密、身份认证、权限隔离、审计日志、防注入全链路覆盖，满足等保 2.0 二级要求 |
| **国产兼容** | 天地图/高德 GIS、GB/T 28181 国标、DJI 无人机生态、国产适配 |

### 1.3 系统边界

合阳洽川湿地智慧管理平台系统的边界明确：**对内**管理湿地范围内的视频设备、无人机、IoT 传感器等硬件资源，通过 AI 分析实现智能告警和工单流转；**对外**通过 GB/T 28181 国标对接上级视频平台，通过标准 API 对接气象局、短信网关等第三方系统。

**不包含的范围**（相较于 V1.0 原始 228 项版本的裁剪说明）：
- 不包含 VR 全景模块（全景内容管理、WebXR 手柄交互等全部移除）
- 不包含完整 IM 即时通讯系统（降级为简版通知+单向/双向文字上报）
- 不包含复杂规则引擎（采用预设模板替代 Drools 可视化编排）
- 不包含演练模式、知识库、智能匹配算法
- 不包含双机热备（降至 99% 可用性，单机主从+每日备份）
- 视频墙仅支持 1/4 分屏（不支持 9/16 分屏）
- 并发用户降至 30 PC + 50 移动端

### 1.4 三大业务闭环

```
1. 防火闭环
   热成像/烟雾检测 → 告警生成 → 自动截图 → 预设规则匹配等级
   → 创建工单 → 派发巡逻员 → 现场确认 → 处置反馈 → 审核归档

2. 无人机巡逻闭环
   定时任务 → 自动起飞 → 航线巡逻 → 实时直播 → 异常检测
   → 自动返航（环境联动/低电量/手动） → 任务记录 → 飞行数据归档

3. 环境监测闭环
   传感器采集 → 数据入库 → 阈值判断 → (超阈值) 告警生成
   → 工单派发 → (返回) 历史曲线 → 趋势分析
```

### 2.2 架构特点说明

相比 V1.0（228 项版本），V2.0 架构的主要简化点：

1. **移除 VR 全景层**：不再需要 Three.js/WebXR/krpano 等 VR 相关技术栈
2. **IM 降级为简版通知**：去掉独立的 IM 微服务（Go+Tigris），合并到公共服务中，仅支持单向通知+文字上报，无群聊/会商室
3. **告警引擎简化**：去掉 Drools 规则引擎，改用预设模板（JSON 配置），满足 152 项中的 4 类固定规则
4. **工单服务简化**：去掉 Camunda 工作流引擎，改为状态机模式；去掉智能匹配算法，改为就近轮询+人工选择
5. **视频墙简化**：仅支持 1/4 分屏，去掉 9/16 分屏布局管理
6. **部署架构简化**：去掉双机热备设计，PostgreSQL 主从+每日备份即可

#### 4.1.3 视频质量诊断

| 诊断项 | 检测方式 | 频率 | 告警阈值 |
|--------|----------|------|----------|
| 视频信号丢失 | 检测 RTSP 连接状态 | 10s | 连续 3 次心跳超时 |
| 画面冻结 | 帧间差异分析 (SSIM < 0.95) | 30s | 持续 30s 以上 |
| 视频模糊 | Laplacian 方差分析 | 60s | 方差 < 100 |
| 帧率异常 | 实际 fps / 配置 fps | 10s | 偏差 > 50% |

#### 4.1.4 与 V1.0 的差异

- 视频墙简化：只保留 1/4 分屏，去掉 9/16 分屏（对应功能 C-01）
- 回放简化：最多支持 2 路同步回放（非 4 路），满足实际巡检需求

```

                │
                ├── 10秒窗口内去重:
                │     同一设备 + 同一类型 + 坐标距离 < 50m → 丢弃
                │
                ├── 置信度过滤:
                │     火点 < 80% / 烟雾 < 70% → 降级为提示
                │
                └── 预设模板匹配:
                       模板1: 热成像火点 (置信度≥80%) → 一级火警

#### 4.3.3 环境联动返航逻辑

```

  ├── IoT风速传感器 > 10.8 m/s (5级风) ──► 告警 ──► 自动返航
  ├── 雨量传感器 > 0.5 mm/h ──► 告警 ──► 禁止起飞/自动返航
  ├── 无人机自身风速计 > 12 m/s ──► 强制返航
  └── 低电量 < 25% ──► 按最短路程返航

  返航优先级:
  1. 紧急: 信号丢失 + 低电量 ← 最短路径下降

  3. 中: 低电量 ← 从当前点直线返航
  4. 低: 手动一键返航 ← 正常速度返航
```

#### 4.5.1 传感器类型与接入

|-----------|---------|---------|---------|---------|---------|

#### 4.5.2 数据流水线

```
  IoT Sensor ──► MQTT Broker (EMQX)
                    │
                    ├──► 规则引擎 ──► 持久化到 TDengine
                    │       │             (自动创建超级表: sensors)
                    │       │             标签: device_id, type, location
                    │       │             列: ts, value, unit
                    │       │
                    │       ├──► 实时阈值比较
                    │       │       ├──► 单阈值: value > T1 → 告警
                    │       │       └──► 多阈值: T1<T2<T3 → 等级递增
                    │       │
                    │       └──► RabbitMQ ──► Alarm Service
                    │
                    └──► Redis ──► 最新值缓存 (key: sensor:{id}:latest)
                                        TTL: 60s
```

#### 4.5.3 数据保留策略

| 数据粒度 | 保留时长 | 存储位置 | 说明 |
|---------|---------|---------|------|
| 原始数据(10s) | 7 天 | TDengine | 原始采集数据 |
| 1 分钟聚合 | 30 天 | TDengine | avg/max/min |
| 1 小时聚合 | 90 天 | TDengine | avg/max/min |

### 7.3 视频流安全

```
  摄像头 ──► RTSP (内网隔离)
              │
              ▼
  ┌──────────────────────┐
  │ Stream Gateway (Go)  │
  │ ├─ 内部转发: gRPC TLS │
  │ ├─ 对外: HTTPS FLV   │
  │ │     + 鉴权 Token   │
  │ └─ 录制: MinIO       │
  │     预签名 URL       │
  └──────────────────────┘

  播放器访问流程:
  1. 前端请求 stream URL → 后端验证权限 + 生成 5min Token
  2. 返回: wss://stream/...?token=***
  3. Stream Gateway 验证 token → 建立 WebRTC/WebSocket 连接
  4. 过期后自动断开, 需重新获取 token
```

  ├── 单 T4: 32 路 1080p @ 25fps
  ├── 增加 GPU 节点: 每节点 +32 路容量
  └── Triton Model Pipeline: 多模型串联
```

### 9.3 性能优化策略

#### 9.3.1 数据库优化

```
  查询优化:
  ├── 索引: 覆盖索引 + 部分索引 + GiST 空间索引
  ├── 分区表: alarms 按月分区, sensors 按日分区
  ├── 连接池: HikariCP (max=20, min=10, timeout=30s)
  ├── 读写分离: 写走主库, 统计分析走从库
  └── 查询缓存: Redis 缓存热点查询

  时序优化:
  ├── TDengine: 超级表 + 标签过滤
  ├── 降采样: 自动聚合 (10s→1min→1h→1d)
  └── 保留策略: 原始数据7天, 聚合数据90天
```

#### 9.3.2 缓存策略

```
  多级缓存:
  ├── 浏览器缓存: 静态资源 CDN
  ├── Redis 缓存: 热点数据 (设备状态/用户信息/配置)
  │   ├── 读: Cache-Aside (先查缓存, miss 查 DB)
  │   └── 写: Write-Through (先写 DB, 再更新缓存)
  ├── 本地缓存: Caffeine (Java), 设备基础信息 1000条
  └── CDN: 地图瓦片/静态资源

  缓存更新:
  ├── 主动失效: 数据变更后发布 Redis Pub/Sub → 各节点清除本地缓存
  ├── TTL 过期: 短 TTL (设备状态 30s) vs 长 TTL (配置 1h)
  └── 预热: 服务启动时加载核心数据到缓存
```

#### 9.3.3 视频流优化

```
  拉流优化:
  ├── RTSP TCP (非 UDP, 避免丢包)
  ├── 多路复用: 同设备多路播放共用一条 RTSP 连接
  ├── 智能缓冲: 根据网络质量动态调整缓冲大小
  └── 关键帧对齐: IDR 帧间隔 2s

  转码优化:
  ├── GPU NVENC: 硬件编码 H.264/H.265
  ├── 自适应码率: 大屏(1080p) / 移动端(720p)
  └── 截图: 从解码帧直接截取

  播放优化:
  ├── WebRTC: UDP 传输, 丢包重传 + FEC
  └── MSE (Media Source Extensions): 渐进式播放
```

### 9.4 压力测试方案

```
  测试工具:
  ├── 后端 API: Locust / JMeter (300 并发)
  ├── 视频流: 自研 RTSP 模拟器 (200 路虚拟摄像头)
  ├── AI: 批量回放录制视频 (32 路同时分析)
  ├── 传感器: MQTT 模拟器 (500 设备同时上报)
  └── 全链路: 模拟 4 端用户操作

  测试场景:
  ├── 正常负载: 80% 目标并发
  ├── 峰值负载: 150% 目标并发 (30min)
  ├── 稳定性: 72h 持续运行
  ├── 故障注入: Chaos Mesh (Pod 杀掉/网络延迟)
  └── 恢复测试: 主库宕机 → 自动切换 → 恢复验证
```
