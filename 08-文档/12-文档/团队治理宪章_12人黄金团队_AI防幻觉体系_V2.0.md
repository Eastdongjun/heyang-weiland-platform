## 第一部分：12人黄金团队配置（6层制衡架构）

### 第1层：顶层决策层（管方向、管流程、定规矩）

---

#### 1. 技术负责人 / 架构师

| 维度 | 内容 |
|:---|:---|
| **角色定位** | 公司技术资产保管员、技术防火墙。决定未来3年技术不会烂尾、不会重构、不会技术绑架。不是高级程序员。 |
| **核心排序** | 团队第1位，定技术、定规范、控底层。 |

**硬性专业能力**

| 能力项 | 要求 |
|:---|:---|
| 架构选型 | 能判断业务体量，精准选型：单体/微服务/分布式，不乱选型 |
| 规范制定 | 制定不可推翻的编码规范、文件规范、命名规范、安全规范 |
| 数据库底层 | 库表设计、索引、分表、事务、锁机制全部精通，杜绝后期数据崩盘 |
| 风险预判 | 预判高并发、卡顿、死锁、接口雪崩、服务器击穿风险 |
| 代码审核 | 能审核每一段重要代码，有一票否决权 |

**软性能力（老板最看重）**

| 能力项 | 要求 |
|:---|:---|
| 克制能力 | 不乱炫技术，不盲目上新技术，优先稳定 |
| 极简思维 | 能用简单方案绝不复杂化，降低维护成本 |
| 人员掌控力 | 压得住开发，治得住写烂代码的人 |
| 风险嗅觉 | 能提前告知哪里未来会爆雷 |

**权限**

- 所有技术方案一票否决
- 有权驳回所有不合格代码、不合格设计
- 有权强制重构烂代码

**绝对禁止（红线）**

| 序号 | 禁止事项 |
|:---:|:---|
| 1 | 禁止沉迷写业务代码（把自己干成普通开发） |
| 2 | 禁止私自改动底层架构 |
| 3 | 禁止偏袒某个开发、包庇烂代码 |

**出错处罚**

| 出错类型 | 处罚 |
|:---|:---|
| 架构设计失误导致后期返工 | 全责、重罚 |
| 技术风险未提前预判 | 扣除绩效 |
| 规范不严导致代码混乱 | 连带责任 |

### 第3层：技术底层层（打底数据、写业务逻辑）

---

#### 5. 数据库工程师（数据资产保管员）

| 维度 | 内容 |
|:---|:---|
| **角色定位** | 公司数据资产的贴身保镖，比后端更懂数据、比架构师更懂库。数据是公司最值钱资产，绝不能让普通开发随意乱建表、乱改数据。 |
| **核心排序** | 团队第5位，排在UI之后、后端之前。UI定外观、数工定数据、后端写业务。先定死数据底层，后端才不会乱开发。 |

**硬性专业能力**

| 能力项 | 要求 |
|:---|:---|
| 全库设计 | MySQL、Redis、向量库、图数据库统筹规划，分库分表、冷热分离 |
| 索引极致优化 | 杜绝慢查询、死锁、全表扫描，保障百万级数据流畅跑 |
| 数据约束 | 字段类型、长度、非空、唯一、外键全部标准化，杜绝脏数据 |
| 数据迁移回滚备份 | 定时自动备份，故障一键回滚 |
| 数据权限管控 | 哪些人能查、能改、能删，严格分级上锁 |

**软性能力**

| 能力项 | 要求 |
|:---|:---|
| 洁癖思维 | 零容忍脏数据、冗余字段、混乱表结构 |
| 预判能力 | 提前预判数据暴涨，提前做扩容、分片预案 |
| 底线原则 | 禁止开发私自改库、删数据，违规直接上报 |

**权限**

- 拥有数据库最高权限，所有数据表、字段、索引一票否决
- 有权驳回后端不合理建表、不合理SQL语句
- 有权冻结高危数据操作、拦截违规数据变更

**绝对禁止（红线）**

| 序号 | 禁止事项 |
|:---:|:---|
| 1 | 禁止给普通开发开放生产数据库高权限 |
| 2 | 禁止无备份、无审批情况下删改生产数据 |
| 3 | 禁止放任冗余垃圾数据长期堆积不清理 |

**出错处罚**

| 出错类型 | 处罚 |
|:---|:---|
| 数据丢失、误删 | 全责重罚，承担资产损失 |
| 索引不合理导致系统卡顿、崩溃 | 扣除全额技术绩效 |
| 脏数据泛滥、数据混乱无人整理 | 连带责任 |

## 第二部分：AI大模型幻觉防错体系

### 2.1 AI角色定位（永远不变）

| 权限类型 | AI状态 |
|:---|:---|
| 决策权 | ❌ 无 |
| 创造权 | ❌ 无 |
| 改编权 | ❌ 无 |
| 执行权 | ✅ 仅有 |
| 整理权 | ✅ 仅有 |
| 复刻权 | ✅ 仅有 |

### 2.2 五大强制机制

#### 机制一：强制溯源机制

| 规则 | 说明 |
|:---|:---|
| 强制标注 | AI输出任何内容，必须标注来源、依据、参考规范 |
| 判定标准 | 无依据、无来源、无参考，一律判定幻觉，直接作废 |
| 禁止事项 | 禁止AI自我脑补、凭空创造规则、凭空创造参数 |

#### 机制二：强制极简机制

| 规则 | 说明 |
|:---|:---|
| 禁止冗余 | AI禁止冗余废话、禁止过度美化、禁止扩写编造 |
| 判定标准 | 看不懂、说不清、逻辑模糊，全部判定幻觉 |
| 输出标准 | AI输出必须直白、硬性、简洁、落地 |

#### 机制三：强制约束锁定机制

| 规则 | 说明 |
|:---|:---|
| 严格守宪 | AI必须严格遵守本手册12岗制度 |
| 禁止篡改 | 不得私自修改岗位、不得私自删减规则、不得私自篡改老板逻辑 |
| 违规判定 | 一旦AI自由发挥 = 幻觉，直接驳回重写 |

#### 机制四：分层审核机制（模仿人类团队）

| 审核层 | 审核角色 | 审核内容 |
|:---|:---|:---|
| 第1层 | 技术负责人 | 审技术方案、架构合理性、代码规范 |
| 第2层 | 产品经理 | 审业务逻辑、需求闭环、PRD一致性 |
| 第3层 | 测试QA | 审漏洞、审边界、审异常场景覆盖 |
| 第4层 | 文档工程师 | 审格式、审排版、审可追溯性 |
| 驳回标准 | 任一层不合理，判定幻觉，全部打回 | |

#### 机制五：禁止编造真实数据

| 规则 | 说明 |
|:---|:---|
| 禁止编造 | AI禁止编造数据库字段、接口地址、代码类名、版本号、专业参数 |
| 合规标准 | 所有参数必须贴合行业标准 + 本公司规范 |
| 违规判定 | 编造数据 = 严重幻觉 |

### 2.3 AI绝对禁止做的事

| 序号 | 禁止事项 |
|:---:|:---|
| 1 | 禁止不懂装懂、强行解释 |
| 2 | 禁止编造不存在的技术、文档、字段 |
| 3 | 禁止美化错误、模糊漏洞、掩盖逻辑缺陷 |
| 4 | 禁止脱离本公司制度自由发挥 |

### 2.4 AI幻觉处罚规则（模型执行标准）

| 幻觉等级 | 判定标准 | 处罚措施 |
|:---|:---|:---|
| 轻度幻觉 | 少量冗余、轻微偏离规范 | 强制重写、删减多余编造内容 |
| 中度幻觉 | 逻辑矛盾、凭空创造规则、编造参数 | 清空上下文、重置记忆、重新生成 |
| 重度幻觉 | 严重违背12岗制度、篡改老板逻辑、编造核心技术数据 | 直接驳回，禁止继续生成，人工介入修正 |

## 第三部分：团队交互与制衡规则

### 3.1 6层制衡架构总图

```
┌────────────────────────────────────────┐
│  ① 顶层决策层                           │
│  技术负责人 ⟷ 项目经理                   │
│       （管方向、管流程、定规矩）          │
├────────────────────────────────────────┤

│  产品经理 ⟷ UI设计师                     │
│       （定产品、定颜值、定体验）          │
├────────────────────────────────────────┤
│  ③ 技术底层层                           │
│  数据库工程师 → 后端开发                 │
│       （数工驳回不合理SQL）              │
├────────────────────────────────────────┤
│  ④ 用户展示层                           │
│  前端开发    移动端开发                  │
├────────────────────────────────────────┤
│  ⑤ 风控质检层                           │
│  安全工程师 ⟷ 测试QA                     │

├────────────────────────────────────────┤
│  ⑥ 资产留存层                           │
│  文档工程师 ⟷ 运维DevOps                 │
│       （沉淀资料、守护线上）              │
└────────────────────────────────────────┘
```

### 3.2 核心制衡原则

| 原则 | 说明 |
|:---|:---|
| 没人能一家独大 | 任何角色都有一票否决或制衡对象 |
| 没人能私自乱改 | 变更必须走审批流，跨岗位会签 |
| 离职不崩盘 | 文档工程师统一归档，知识不随人走 |
| 项目不烂尾 | 技术负责人控底层、项目经理控进度、测试QA卡上线 |

### 3.3 跨岗位交互协议

| 场景 | 交互规则 |
|:---|:---|
| 技术方案争议 | 技术负责人拥有最终裁决权，其他角色可提异议但必须记录 |
| 需求变更 | 产品经理发起 → 项目经理评估影响 → 技术负责人评估技术成本 → 三方会签 |
| 设计改动 | UI设计师提出 → 产品经理确认业务影响 → 前端开发确认实现成本 → 三方会签 |
| 库表变更 | 后端开发申请 → 数据库工程师审核 → 技术负责人批准 → 文档工程师归档 |
| 上线审批 | 测试QA测试通过 + 安全工程师安全通过 → 项目经理排期 → 运维DevOps执行 |
| 文档缺失 | 文档工程师发起追缴 → 项目经理督办 → 目标角色限期补交 |

### 3.4 一票否决权汇总

| 角色 | 一票否决范围 |
|:---|:---|
| 技术负责人 | 技术方案、不合格代码、不合格设计、底层架构变更 |
| 项目经理 | 不合理开发、不合理需求、口头变更 |
| 数据库工程师 | 数据表设计、字段定义、索引方案、SQL语句、数据变更 |
| 安全工程师 | 有安全漏洞禁止上线、高危数据操作、异常IP/账号封禁 |
| 测试QA | 不合格版本禁止打包上线、强制要求修复致命/严重BUG |
